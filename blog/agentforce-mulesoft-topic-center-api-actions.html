Salesforce Agentforce + MuleSoft End-to-End: Topic Center, API Catalog & External Actions Setup

Expose SAP S/4HANA, ERP, and Snowflake operations directly to the Salesforce Atlas Reasoning Engine using MuleSoft Topic Center, Anypoint Exchange, and Salesforce API Catalog — with zero custom Apex callout boilerplate.

✍️ Niranjan Potter 📅 Nov 24, 2026 ⏱️ 19 min read AgentforceTopic Center

TL;DR

  • Eliminate Apex glue code: Connect Anypoint Platform and Salesforce at the tenant level so governed MuleSoft APIs synchronize natively into Salesforce API Catalog as External Services and Agentforce Topics & Actions.
  • Shift agent semantics left in ACB: Use MuleSoft Topic Center in Anypoint Code Builder (ACB) to author Topics, classification descriptions, scopes, natural-language action instructions, and API Governance checks right next to your OpenAPI 3.0 contract.
  • Shape payloads for Atlas Reasoning Engine: Flatten deeply nested SAP BAPI/OData and Snowflake responses inside DataWeave 2.0 so the Atlas LLM selects slots accurately, minimizes prompt token burn, and avoids hallucinating field paths.
  • Enforce zero-trust OAuth 2.0 end-to-end: Bind API Manager policies on CloudHub 2.0 to Salesforce Named Credentials + External Credentials (client_credentials or JWT Bearer) with human-in-the-loop confirmation instructions before any mutating POST/PATCH call.
  • Verify in Agent Builder Plan Tracer: Inspect every step of the Atlas loop — Topic classification, slot extraction, grounding, MuleSoft HTTP invocation, and final answer synthesis — before activating the agent on Experience Cloud or Slack.

What it is and why it matters

Before native Agentforce-to-MuleSoft catalog synchronization, exposing an enterprise ERP or data warehouse capability to a Salesforce copilot meant hand-rolling an @InvocableMethod Apex wrapper, writing HttpRequest serialization classes, maintaining duplicate credential secrets, and pasting brittle prompt instructions inside Salesforce org metadata. Every time an API field changed in SAP S/4HANA or Snowflake, Apex classes drifted out of sync and broke silently at runtime.

The joint MuleSoft Topic Center + Salesforce API Catalog architecture replaces bespoke callout wrappers with a declarative, contract-first pipeline across five phases:

  1. Bi-directional Tenant Trust: Links your Salesforce org and selected Anypoint Platform Business Groups over a platform-managed trust relationship.
  2. Topic Center in Anypoint Code Builder: Enriches standard OpenAPI 3.0 specifications with agentic metadata — Topics, Classification Descriptions, Scope, Agent Actions, and Instructions — validated by Anypoint API Governance rulesets.
  3. Managed Runtime & Exchange Publication: Deploys the Mule 4 application to CloudHub 2.0 behind API Manager OAuth 2.0 policies and publishes the Topic-enabled asset to Anypoint Exchange.
  4. Salesforce API Catalog Sync: Discovers managed Exchange APIs inside Salesforce Setup and auto-generates External Credentials, Named Credentials, and External Services action bindings.
  5. Agentforce Studio (Agent Builder): Attaches synchronized MuleSoft Topics and Actions to Service or Employee Agents so the Atlas Reasoning Engine plans and executes cross-system workflows autonomously.

Why flat Experience API schemas beat raw ERP payloads for Atlas

Raw SAP S/4HANA A_SalesOrder OData payloads routinely return 180+ fields across nested to_Item, to_Partner, and to_ScheduleLine navigation arrays, using cryptic four-character ABAP codes (LFSTK, GBSTK, WERKS). Feeding raw System API payloads directly to an LLM degrades reasoning in three ways:

  • Slot confusion: Ambiguous field names (VBELN vs BSTNK) cause the Atlas planner to pass a customer PO number where a 10-digit SAP Sales Order ID is expected.
  • Context window bloat & latency: Returning 60 KB of nested item schedules consumes thousands of input tokens per reasoning turn, pushing multi-turn latency past the interactive threshold.
  • Schema compilation limits: Salesforce External Services rejects deeply recursive or unconstrained polymorphic (anyOf without discriminator) schemas.

Placing a MuleSoft Experience/Agent API in front of SAP and Snowflake lets DataWeave 2.0 project a clean, flat, domain-labeled JSON contract (salesOrderNumber, deliveryStatus, estimatedDeliveryDate, warehouseStockAvailable) tailored specifically for deterministic agent reasoning.

Prerequisites

You need
  • Salesforce Org: Enterprise, Performance, or Unlimited Edition (or Agentforce Developer Org) with Salesforce Foundations, Einstein Generative AI, Agentforce Agents, and API Catalog enabled.
  • Salesforce Permissions: System Administrator plus Customize Application, Manage Named Credentials, Manage External Services, and Configure Agentforce Agents permission sets.
  • Anypoint Platform Access: Organization Administrator (one-time tenant link in Access Management), Exchange Contributor, and API Manager Environment Administrator on the target Business Group.
  • IDE & Tooling: Anypoint Code Builder (ACB Desktop in VS Code or Cloud IDE, late-2025+ release with Topic Center enabled), JDK 17, Maven 3.9+, and Mule Runtime 4.9.0.
  • OAuth 2.0 Identity Provider: An Anypoint Connected App (client_credentials grant with API access scope) or enterprise OIDC provider (Okta, Microsoft Entra ID, Salesforce External Client App) configured in API Manager.

Step-by-step setup

  1. Phase 1: Establish Tenant Trust between Salesforce and Anypoint Platform

    Start by creating the platform-level trust handshake so Salesforce API Catalog can read governed APIs from specific Anypoint Business Groups without sharing personal user passwords.

    In Salesforce Setup, search for Anypoint Platform Setup in Quick Find. Copy your Salesforce Org Tenant Key (or click Connect to Anypoint Platform depending on your org region — US vs EU Control Plane). Next, sign in to Anypoint Platform → Access Management → Salesforce as an Organization Administrator:

    • Verify your linked Salesforce Org ID (00D...) appears in the connected orgs table and toggle its status to Enabled.
    • Click Manage Access / Business Groups and select only the curated Business Groups (for example, Enterprise-Agent-APIs) and environments (Sandbox, Production) that should surface in Salesforce API Catalog. Avoid exposing raw internal System API Business Groups.
  2. Phase 2: Author API Contract & Agentic Metadata in ACB Topic Center

    Open Anypoint Code Builder and create a new API Specification project (erp-order-fulfillment-agent-api) using OpenAPI 3.0.3. Every operation exposed to Agentforce must define a unique operationId, clear summary and description strings, explicit parameter constraints, and flat request/response schemas.

    Next, open the Topic Center panel in ACB (MuleSoft: Open Topic Center from the Command Palette). Topic Center reads your OpenAPI operations and generates (or lets you refine) structured agentic metadata:

    • Topic Label & Name: ERP_Order_And_Inventory_Management — groups cohesive actions so Atlas loads only relevant tool definitions per turn.
    • Classification Description: Explains in 1–3 sentences when Atlas should route an utterance into this Topic (e.g., checking ERP fulfillment state, carrier tracking, warehouse stock in Snowflake, or expediting unshipped orders).
    • Scope: Defines the agent's boundary and persona permissions within this Topic.
    • Agent Instructions & Action Mapping: Maps each OpenAPI operationId to an Agent Action and attaches guardrails (for instance, requiring explicit customer confirmation of the surcharge before invoking expediteSalesOrderShipment).

    Before publishing, run Anypoint API Governance validation inside ACB with the Agentforce Readiness / Topic Governance ruleset to verify there are no missing operationIds, unbounded string inputs, or undocumented HTTP error codes.

    .anypoint/governance-check.sh 
    anypoint-cli-v4 governance:api:validate \
  --specification src/main/resources/api/erp-order-fulfillment-api.yaml \
  --rulesets exchange_modules/org.mule.governance/agentforce-topic-readiness/1.1.0/ruleset.yaml
  3. Phase 3: Implement in Mule 4.9, Register in API Manager & Publish to Exchange

    Scaffold the Mule 4.9 implementation from your governed OpenAPI spec in ACB (MuleSoft: Implement this Local API). Implement orchestration flows that call SAP S/4HANA and Snowflake, flatten the payload via DataWeave, and deploy the application to CloudHub 2.0.

    Crucially, Salesforce API Catalog only activates invocable actions for Exchange assets backed by managed endpoint metadata:

    • In API Manager, create an API instance (Mule Gateway / Flex Gateway) pointing to your Exchange asset, record the API Instance ID (19482751), and apply an OAuth 2.0 Access Token Enforcement policy (or Client ID Enforcement on dedicated mTLS ingress).
    • Set the Consumer Endpoint URL (https://erp-order-agent-api.us-e2.cloudhub.io/api/v1) on the API Manager instance so Exchange exports the exact target host during Salesforce catalog sync.
    • Publish the Topic-enabled specification + Topic metadata bundle to Anypoint Exchange in your enabled Business Group.
  4. Phase 4: Synchronize Salesforce API Catalog, Named Credentials & External Services

    Switch back to Salesforce Setup → API Catalog, select the MuleSoft tab, and click Sync Catalog (sync runs asynchronously and typically completes within 1–2 minutes). Locate ERP Order Fulfillment Agent API in the catalog list:

    • Verify the Agent Topic Available badge is shown alongside the three OpenAPI operations.
    • Click Activate Actions. Salesforce prompts you to bind or generate an External Credential and Named Credential (Mule_ERP_Fulfillment_NC) for the CloudHub 2.0 Consumer Endpoint URL, then compiles the OpenAPI contract into External Services invocable actions.
    • Navigate to Setup → Named Credentials → External Credentials, open Mule_ERP_Fulfillment_EC, configure the OAuth 2.0 client_credentials token URL and client secret, and grant your Agentforce Service User's Permission Set access under External Credential Principal Access.
    Don't skip Principal Access mapping

    Even when using a machine-to-machine client_credentials flow, Salesforce requires the running user (for autonomous Service Agents, the EinsteinServiceAgent User profile/permission set) to be mapped to the Named Credential's External Credential Principal — otherwise External Services throws an INSUFFICIENT_ACCESS_OR_READONLY callout exception at runtime.

  5. Phase 5: Wire Topic & Actions in Agentforce Studio (Agent Builder)

    Go to Salesforce Setup → Agents, select your target agent (for example, B2B Order Support Agent), and click Open in Builder (deactivate the agent first if currently active):

    • In the Topics sidebar, click New → Add from Asset Library / API Catalog and select the synchronized MuleSoft Topic ERP Order and Inventory Management.
    • Inspect the imported Classification Description, Scope, and Instructions authored in ACB Topic Center — no manual copy-pasting required.
    • Open the This Topic's Actions tab and verify all three ExternalService actions (getOrderFulfillmentStatus, checkWarehouseStockSnowflake, expediteSalesOrderShipment) are attached with input/output parameter descriptions intact.
    • Click Activate once Reasoning Trace testing passes.

1. Agent-optimized OpenAPI 3.0.3 contract

Notice how every property uses explicit domain names, bounded patterns, and unambiguous descriptions so the Atlas LLM extracts slot values reliably.

src/main/resources/api/erp-order-fulfillment-api.yaml

info:
  title: ERP Order Fulfillment Agent API
  version: 1.2.0
  description: >
    Agent-optimized Experience API exposing real-time SAP S/4HANA sales order
    fulfillment status, Snowflake warehouse stock availability, and expedited
    shipping upgrades to Salesforce Agentforce.
servers:
  - url: https://erp-order-agent-api.us-e2.cloudhub.io/api/v1
    description: CloudHub 2.0 Production Consumer Endpoint
security:
  - oauth2ClientCredentials:
      - erp:orders:read
      - erp:orders:write
paths:
  /orders/{salesOrderNumber}/status:
    get:
      operationId: getOrderFulfillmentStatus
      summary: Retrieve live SAP S/4HANA fulfillment and carrier status for a sales order
      description: >
        Fetches current fulfillment stage, carrier tracking, shipping tier, and
        estimated delivery date for an 8-to-10 digit numeric SAP Sales Order number.
        Strip any leading 'SO-' prefix before calling this action.
      parameters:
        - name: salesOrderNumber
          in: path
          required: true
          description: Numeric SAP Sales Order ID (8 to 10 digits, e.g. 00904128). Not a customer PO number.
          schema:
            type: string
            pattern: '^[0-9]{8,10}$'
      responses:
        '200':
          description: Flattened sales order fulfillment summary
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/OrderStatusResponse'
        '404':
          description: Sales order not found in SAP S/4HANA
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/AgentErrorResponse'

  /inventory/{sku}/availability:
    get:
      operationId: checkWarehouseStockSnowflake
      summary: Check real-time available-to-promise stock across regional warehouses
      description: >
        Queries Snowflake LIVE_WAREHOUSE_INVENTORY for available-to-promise (ATP)
        units by product SKU and optional region code (US-EAST, US-WEST, EU-CENTRAL).
      parameters:
        - name: sku
          in: path
          required: true
          description: Alphanumeric product SKU (e.g. IND-VALVE-400X)
          schema:
            type: string
        - name: region
          in: query
          required: false
          description: Optional warehouse region filter (US-EAST, US-WEST, EU-CENTRAL)
          schema:
            type: string
            enum: [US-EAST, US-WEST, EU-CENTRAL]
      responses:
        '200':
          description: Available-to-promise warehouse inventory summary
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/InventoryAvailabilityResponse'

  /orders/{salesOrderNumber}/expedite:

      summary: Upgrade an unshipped SAP sales order to Priority Overnight shipping

        Mutating action that upgrades shipping condition in SAP S/4HANA to Priority

        'DELIVERED' AND after the user explicitly confirms the expedite fee.
      parameters:
        - name: salesOrderNumber
          in: path
          required: true
          description: Numeric SAP Sales Order ID (8 to 10 digits)
          schema:
            type: string
            pattern: '^[0-9]{8,10}$'
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/ExpediteOrderRequest'
      responses:
        '200':
          description: Shipping tier upgraded in SAP S/4HANA
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ExpediteOrderResponse'

components:
  securitySchemes:
    oauth2ClientCredentials:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://anypoint.mulesoft.com/accounts/api/v2/oauth2/token
          scopes:
            erp:orders:read: Read ERP order and warehouse status
            erp:orders:write: Modify shipping tier on unshipped ERP orders
  schemas:
    OrderStatusResponse:
      type: object
      required: [salesOrderNumber, deliveryStatus, shippingTier, expediteEligible]
      properties:
        salesOrderNumber:
          type: string
        customerPoNumber:
          type: string
        deliveryStatus:
          type: string
          enum: [ORDER_RECEIVED, PICKING_IN_WAREHOUSE, PACKED, SHIPPED, DELIVERED, ON_CREDIT_HOLD]
        shippingTier:
          type: string
        carrierName:
          type: string
        trackingNumber:
          type: string
        estimatedDeliveryDate:
          type: string
          format: date

2. ACB Topic Center semantic metadata

In ACB Topic Center, this descriptor binds your OpenAPI operations to an Agentforce Topic with classification criteria, scope, and deterministic pre-execution instructions.

src/main/resources/topic-center/erp-order-topic.yaml 
schemaVersion: "1.0"
topic:
  apiName: ERP_Order_And_Inventory_Management
  label: ERP Order and Inventory Management
  classificationDescription: >
    Use this topic when a customer or account rep asks about real-time B2B sales
    order fulfillment status in SAP, carrier tracking, warehouse stock availability
    by SKU, or upgrading/expediting shipping speed on an existing order.
  scope: >
    Your job is solely to inspect live order fulfillment status, verify warehouse
    inventory availability, and process approved shipping tier upgrades for valid
    SAP Sales Orders. Never modify order line quantities, pricing, or billing addresses.
  instructions:
    - >
      Always normalize Sales Order IDs by stripping prefixes like 'SO-' or '#' so
      only the 8-to-10 digit numeric string (padded with leading zeros if 7 digits,
      e.g. '00904128') is passed to getOrderFulfillmentStatus.
    - >
      If the user provides a Customer PO Number (e.g. 'PO-ACME-99') instead of a
      numeric SAP Sales Order ID, ask the user for the SAP Sales Order ID or look
      it up via Salesforce Order records first.
    - >
      Before calling expediteSalesOrderShipment, you MUST first call
      getOrderFulfillmentStatus in the same session to verify expediteEligible is
      true. If deliveryStatus is SHIPPED, DELIVERED, or ON_CREDIT_HOLD, explain
      why the order cannot be expedited and do not invoke the expedite action.
    - >
      CRITICAL MUTATION GUARDRAIL: Never call expediteSalesOrderShipment until you
      explicitly state the exact expediteFeeUsd to the user and receive an unambiguous
      affirmative reply in a subsequent turn.
  actions:
    - operationId: getOrderFulfillmentStatus
      actionLabel: Get ERP Order Fulfillment Status
      requireUserConfirmation: false
    - operationId: checkWarehouseStockSnowflake
      actionLabel: Check Warehouse Stock in Snowflake
      requireUserConfirmation: false
    - operationId: expediteSalesOrderShipment
      actionLabel: Expedite ERP Sales Order Shipment
      requireUserConfirmation: true

Here is the externalized DataWeave 2.0 script that translates cryptic SAP ABAP delivery/credit codes (OverallSDProcessStatus, TotalCreditCheckStatus, ShippingCondition) into clean domain enums and strips internal cost/margin fields before the payload ever reaches the LLM:

src/main/resources/dw/flatten-sap-order-status.dwl 
%dw 2.0
output application/json skipNullOn="everywhere"

fun mapDeliveryStatus(creditCode: String | Null, deliveryCode: String | Null) =
  if (creditCode == "B" or creditCode == "C") "ON_CREDIT_HOLD"
  else deliveryCode match {
    case "A" -> "ORDER_RECEIVED"
    case "B" -> "PICKING_IN_WAREHOUSE"
    case "C" -> "SHIPPED"
    case "D" -> "DELIVERED"
    else     -> "PACKED"
  }

var status = mapDeliveryStatus(payload.TotalCreditCheckStatus, payload.OverallDeliveryStatus)
var firstItem = payload."_Item"[0] default {}
---
{
  salesOrderNumber: payload.SalesOrder,
  customerPoNumber: payload.PurchaseOrderByCustomer,
  deliveryStatus: status,
  shippingTier: if (payload.ShippingCondition == "01") "PRIORITY_OVERNIGHT" else "STANDARD_GROUND",
  carrierName: payload.YY1_CarrierName_SDH,
  trackingNumber: payload.YY1_TrackingNum_SDH,
  estimatedDeliveryDate: firstItem."_ScheduleLine"[0].ConfirmedDeliveryDate,
  expediteEligible: (status == "ORDER_RECEIVED" or status == "PICKING_IN_WAREHOUSE")
                    and payload.ShippingCondition != "01",
  expediteFeeUsd: 45.00,
  primarySku: firstItem.Material
}

Deploy to production

Enterprise teams promote Agentforce + MuleSoft integrations across Dev → UAT → Prod without manually re-editing Topics in Agent Builder:

  • Promote the Mule 4 artifact & API Manager instance: Deploy the immutable JAR to CloudHub 2.0 (mvn deploy -DmuleDeploy) in at least 2 replicas (0.2 vCore or higher) with Zero-Downtime Rolling Updates enabled, and promote the API Manager configuration from UAT to Production.
  • Keep Exchange asset coordinates stable: Publish patch/minor versions (1.2.1) under the same groupId:assetId in Anypoint Exchange and re-sync Salesforce API Catalog only when the OpenAPI schema or Topic instructions change.
  • Swap Named Credential URLs per Salesforce org: Deploy GenAiPlugin (Topic), GenAiFunction (Action), and ExternalServiceRegistration metadata via SFDX (sf project deploy start), while binding environment-specific CloudHub 2.0 URLs and OAuth client secrets inside each org's NamedCredential / ExternalCredential.
  • Enforce tight downstream timeouts: Agentforce synchronous External Service actions expect responses well within interactive chat budgets. Set HTTP request timeouts on SAP/Snowflake connectors to 6–8 seconds with fallback agentGuidance messages if an ERP batch lock occurs.

Security & governance

  • Least-privilege Business Group scoping: In Anypoint *Access Management → Salesforce*, never enable the root Organization if it contains raw System or Process APIs. Create a dedicated Agent-Experience-APIs Business Group containing only vetted, agent-safe contracts.
  • User context & row-level authorization: Machine-to-machine client_credentials authenticates Salesforce as a trusted caller, not the end user. For customer-facing Experience Cloud agents, pass the verified Contact/Account identifier or use OAuth 2.0 JWT Bearer / Named Principal per-user token exchange and assert ownership in MuleSoft (order.soldToAccountId == callerAccountId) so prompt injection cannot trick the agent into reading another customer's order (IDOR prevention).
  • PII stripping at the MuleSoft boundary: Never return full credit card numbers, tax IDs, internal wholesale margins, or employee SSNs in Agent API schemas — DataWeave skipNullOn + explicit field allowlisting keeps sensitive fields out of both the Einstein Trust Layer audit log and LLM context.
  • Defense-in-depth on mutating actions: Pair natural-language confirmation instructions (requireUserConfirmation: true in Agentforce) with hard schema validation in API Manager (JSON Threat Protection, Rate Limiting SLA tiers, and Object Store idempotency keys) so duplicate retries never double-charge customers in SAP.

Either the Business Group isn't shared in Access Management → Salesforce, or the Exchange asset has no active API Manager instance with a Consumer Endpoint URL. Enable the specific Business Group under Access Management → Salesforce, set a valid HTTPS Consumer Endpoint URL in API Manager, and click Sync Catalog again.
Clicking Activate Actions in API Catalog fails with External Service schema compilation error. Refactor the Agent Experience API spec to flat, explicitly typed JSON objects and run the ACB Agentforce Readiness API Governance ruleset before republishing.
Agent Builder Plan Tracer shows 401 Unauthorized or CalloutException: Unable to fetch OAuth token. EinsteinServiceAgent User lacks External Credential Principal Access, or the Connected App lacks the required API Manager scope. Assign a Permission Set granting External Credential Principal Access for Mule_ERP_Fulfillment_EC to the Agent User and verify token issuance via curl.
Atlas Reasoning Engine invokes getOrderFulfillmentStatus with "SO-00904128" and receives 400 Bad Request. Atlas calls expediteSalesOrderShipment immediately on Turn 1 without asking user approval. Production checklist

  • Anypoint Platform ↔ Salesforce tenant trust restricted to dedicated Agent-Experience-APIs Business Group (no raw System APIs exposed).
  • Every OpenAPI operation has a unique operationId, flat typed schemas (< 15 fields), and passes the ACB Agentforce API Governance ruleset.
  • Topic Center metadata defines unambiguous classificationDescription, bounded scope, and explicit confirmation guardrails on every mutating action.
  • API Manager instance enforces OAuth 2.0 Token Enforcement, Rate Limiting, and JSON Threat Protection ahead of the Mule 4 runtime.
  • Salesforce ExternalCredential uses OAuth 2.0 (client_credentials or JWT Bearer) and EinsteinServiceAgent User holds Principal Access permission.
  • Mule 4 implementation enforces tenant/customer ownership checks (IDOR protection) and Object Store idempotency on POST/PATCH flows.
  • DataWeave transforms strip PII, internal cost fields, and stack traces, returning structured agentGuidance on 4xx/5xx errors.
  • Multi-turn adversarial and edge-case utterances verified in Agentforce Builder Plan Tracer / Testing Center before channel activation.

Interview questions

1. Why should architects expose an Agent Experience API via MuleSoft Topic Center instead of pointing Salesforce External Services directly at SAP S/4HANA or Snowflake APIs?

Pointing External Services directly at a backend ERP leaks brittle, deeply nested schemas (hundreds of cryptic ABAP/SQL columns) into the Atlas Reasoning Engine, inflating token usage, confusing slot extraction, and frequently violating External Services OpenAPI compiler limits. An Agent Experience API authored with Topic Center lets MuleSoft orchestrate multiple backends (SAP + Snowflake) in a single network hop, flatten and mask sensitive fields with DataWeave, enforce centralized API Manager rate/OAuth policies, and embed reusable Topic & Action instructions directly in Anypoint Exchange.

2. How does the Atlas Reasoning Engine decide which MuleSoft action to invoke during a conversation turn?

Atlas uses a two-stage hierarchical selection loop. First, it evaluates the user's utterance and conversation history against the Classification Description of every Topic assigned to the agent to narrow the active toolset to one Topic (for example, ERP_Order_And_Inventory_Management). Second, inside that Topic's Scope and Instructions, Atlas inspects the description and JSON input schema of each attached Action (derived from your OpenAPI operationId, description, and parameter descriptions) to build a grounded execution plan.

3. What is required in Anypoint Platform for an API specification to appear with activatable actions inside Salesforce API Catalog?

Four conditions must hold: (1) the bi-directional tenant connection must be enabled in both Salesforce Anypoint Platform Setup and Anypoint Access Management → Salesforce; (2) the target Anypoint Business Group must be explicitly shared with that Salesforce org; (3) the OpenAPI 3.0 asset (optionally enriched via Topic Center) must be published to Anypoint Exchange in that Business Group; and (4) the asset must be associated with an active API Manager instance that defines a valid HTTPS Consumer Endpoint URL.

4. How do you prevent Broken Object-Level Authorization (BOLA / IDOR) when Agentforce calls MuleSoft over a machine-to-machine OAuth 2.0 Client Credentials Named Credential?

Because client_credentials authenticates the Salesforce org rather than the individual Experience Cloud customer, relying solely on user-supplied prompt text ("check order 00904128") allows a user to probe another customer's order ID. Prevent this by binding the verified session ContactId / AccountId from Agentforce context variables (not editable by prompt text) or using per-user JWT Bearer token propagation, and asserting inside the Mule 4 flow that sapOrder.SoldToParty == verifiedAccountErpId before returning any data.

5. How should a MuleSoft API format 4xx and 5xx error payloads when the caller is an autonomous AI agent rather than a traditional web UI?

Traditional stack traces or numeric ERP codes (SAP-BAPI-E-042) cause LLMs either to retry futilely with the same inputs or give generic apologies. An agent-ready MuleSoft API maps downstream faults to deterministic HTTP status codes (400, 404, 409, 503) paired with a concise JSON object containing errorCode and a natural-language agentGuidance field (for example, "Order is on credit hold; advise the customer to contact Accounts Receivable rather than retrying expedite"), giving the Atlas Reasoning Engine clear next-step instructions.
