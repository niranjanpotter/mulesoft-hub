MuleSoft MCP Connector Hands-On: Build an MCP Server & Client in Mule 4

Learn how to expose governed Mule 4 integration flows as Model Context Protocol (MCP) tools over Streamable HTTP—and consume external MCP servers from Mule orchestrations—using mule-mcp-connector 1.2.0 on Mule 4.9 LTS.

✍️ Niranjan Potter 📅 Nov 24, 2026 ⏱️ 20 min read MCP ConnectorMule 4.9 Hands-On

TL;DR

  • Official Mule 4 plugin: Add com.mulesoft.connectors:mule-mcp-connector:1.2.0 (<classifier>mule-plugin</classifier>) with namespace xmlns:mcp="http://www.mulesoft.org/schema/mule/mcp" to turn any Mule 4.9 application into a standards-compliant MCP server or client.
  • Streamable HTTP first: Use <mcp:streamable-http-server-connection> bound to an existing HTTP Listener at /mcp. Unlike legacy dual-endpoint HTTP+SSE, Streamable HTTP works cleanly across stateless CloudHub 2.0 load balancers and Anypoint Flex Gateway without sticky-session fragility.
  • Schema-first tool contracts: Each <mcp:tool-listener> validates incoming LLM arguments against an inline or externalized JSON Schema via <mcp:tool-input-schema>, mapping parsed fields into #[payload.arguments] before your DataWeave or System API logic runs.
  • Read vs. write safety: Separate side-effect-free queries (lookup-order-status, check-inventory-stock) from state-mutating tools (create-return-rma) with explicit idempotency keys, business guardrails, and structured MCP error responses.
  • Bidirectional Mule MCP: The same connector ships <mcp:client-config>, <mcp:list-tools>, and <mcp:call-tool> so Mule Process APIs and Agent Brokers can invoke third-party MCP servers natively.

What it is and why it matters

Before the Model Context Protocol (MCP), exposing an enterprise ERP or Order Management workflow to Claude, Cursor, Salesforce Agentforce, or custom LangGraph agents meant maintaining N×M bespoke tool wrappers, OpenAPI function-calling shims, and custom authentication glue. Worse, exposing raw System API OpenAPI specs directly to an LLM floods the model context window with dozens of low-level query parameters, internal status codes, and brittle pagination tokens.

The MuleSoft MCP Connector (mule-mcp-connector) embeds JSON-RPC 2.0 MCP protocol framing, capability negotiation (initialize), tool discovery (tools/list), JSON Schema input validation, and structured tool execution (tools/call) directly into the Mule 4 reactive engine. Instead of writing throwaway Python sidecars that bypass your enterprise integration layer, you build coarse-grained, business-intent tools right inside Mule 4—reusing DataWeave 2.0 transformations, NetSuite/SAP/Salesforce connectors, connection pooling, MUnit tests, and Flex Gateway policies.

Why Streamable HTTP beats legacy SSE and stdio in enterprise deployments

Early MCP specifications relied either on local stdio subprocess pipes or a split HTTP+SSE transport (where a long-lived GET /sse stream pushed an ephemeral session endpoint for POST /message). Split SSE breaks immediately behind multi-replica CloudHub 2.0 ingress controllers unless sticky sessions are pinned, and corporate proxies aggressively drop idle SSE sockets. MCP's modern Streamable HTTP transport consolidates client-to-server JSON-RPC requests and optional server-streamed responses onto a single /mcp endpoint with standard HTTP headers (Mcp-Session-Id), scaling horizontally across CloudHub 2.0 and Runtime Fabric replicas.

Transport Mode Wire Mechanism CloudHub 2.0 & Flex Gateway Fit Recommended Enterprise Use
Streamable HTTP (Recommended) Single POST /mcp JSON-RPC 2.0 endpoint (supports chunked SSE upgrade when streaming) Native fit; stateless-friendly, works cleanly with L7 load balancers, OAuth 2.0, and WAFs All production Mule 4 MCP servers on CloudHub 2.0, RTF, and Hybrid
Legacy HTTP + SSE (Deprecated) Persistent GET /sse channel + separate POST /messages?sessionId=... Fragile; fails without sticky session affinity across multi-worker deployments Legacy backwards compatibility only during client migration
stdio OS standard input/output over local child process Not supported on cloud runtimes; zero network auth or central gateway visibility Local developer CLI tools only—never for shared enterprise APIs

Architecture

In the architecture below, AI hosts (Claude Desktop, Cursor, Salesforce Agentforce, or a Mule Orchestrator flow using mcp:call-tool) connect through Anypoint Flex Gateway to a Mule 4.9 MCP Server exposing three coarse-grained commerce tools over Streamable HTTP.

Prerequisites

You need
  • JDK & Runtime: Eclipse Temurin JDK 17 (17.0.11+) and Mule Runtime 4.9.0 LTS (required by mule-mcp-connector 1.2.x).
  • IDE & Maven: Anypoint Code Builder (Oct 2026+ release) or Anypoint Studio 7.20+, and Apache Maven 3.9.6+ configured with Anypoint Enterprise Maven Repository credentials in ~/.m2/settings.xml.
  • Node.js (for MCP Inspector): Node.js 20 LTS+ with npx to run @modelcontextprotocol/inspector locally.
  • Anypoint Permissions: Exchange Viewer (to pull connector artifacts), Runtime Manager Deploy Application, and API Manager Environment Admin.

Step-by-step setup

  1. Create a Mule 4.9 project in Anypoint Code Builder or Studio

    Generate a new Mule project named commerce-ops-mcp-server targeting Mule Runtime 4.9.0 and Java 17. Ensure mule-maven-plugin is version 4.3.0+.

  2. Add the MuleSoft MCP Connector 1.2.0 dependency to pom.xml

    Include mule-mcp-connector with <classifier>mule-plugin</classifier> alongside standard HTTP and Sockets connectors.

    pom.xml 
    <?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.enterprise.mule.ai</groupId>
  <artifactId>commerce-ops-mcp-server</artifactId>
  <version>1.0.0</version>
  <packaging>mule-application</packaging>

  <properties>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <app.runtime>4.9.0</app.runtime>
    <java.version>17</java.version>
    <mule.maven.plugin.version>4.3.1</mule.maven.plugin.version>
    <mule.mcp.connector.version>1.2.0</mule.mcp.connector.version>
  </properties>

  <dependencies>
    <dependency>
      <groupId>com.mulesoft.connectors</groupId>
      <artifactId>mule-mcp-connector</artifactId>
      <version>${mule.mcp.connector.version}</version>
      <classifier>mule-plugin</classifier>
    </dependency>
    <dependency>
      <groupId>org.mule.connectors</groupId>
      <artifactId>mule-http-connector</artifactId>
      <version>1.10.3</version>
      <classifier>mule-plugin</classifier>
    </dependency>
    <dependency>
      <groupId>org.mule.connectors</groupId>
      <artifactId>mule-sockets-connector</artifactId>
      <version>1.2.5</version>
      <classifier>mule-plugin</classifier>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.mule.tools.maven</groupId>
        <artifactId>mule-maven-plugin</artifactId>
        <version>${mule.maven.plugin.version}</version>
        <extensions>true</extensions>
      </plugin>
    </plugins>
  </build>
</project>
  3. Define externalized YAML configuration properties

    Create src/main/resources/config/local.yaml for listener ports, server metadata, downstream System API timeouts, and RMA safety caps.

    src/main/resources/config/local.yaml 
    http:
  host: "0.0.0.0"
  port: "8081"

mcp:
  server:
    name: "commerce-ops-mcp-server"
    version: "1.0.0"
    path: "/mcp"
  client:
    externalShippingMcpUrl: "https://carrier-rates-mcp.internal.enterprise.com/mcp"
    requestTimeoutMs: "8000"

sapi:
  orders:
    host: "orders-sapi.internal.enterprise.com"
    port: "443"
    responseTimeoutMs: "5000"
  rma:
    maxAutoRmaValueUsd: "1500.00"
  4. Declare the MCP XML namespace and Streamable HTTP server config

    Bind <mcp:config> to your shared HTTP_Listener_config at mcpEndpointPath="/mcp" using the official MCP XSD schema location.

  5. Author strict JSON Schemas for each tool's input contract

    Write explicit description, pattern, enum, and additionalProperties: false constraints inside <mcp:tool-input-schema>. High-precision descriptions drastically reduce LLM argument hallucination and trigger automatic MCP:INVALID_ARGUMENTS rejection before hitting downstream ERP APIs.

  6. Shape lean, LLM-friendly responses with DataWeave 2.0

    Never dump a 400-field SAP BAPI response into <mcp:text-tool-response-content>. Project only the 6–10 business fields an agent needs so you conserve context tokens and avoid leaking internal cost/margin columns.

  7. Configure an MCP Client flow for outbound tool consumption

    Add <mcp:client-config> with <mcp:streamable-http-client-connection> so Mule orchestrations can dynamically list and invoke tools hosted on partner or internal MCP servers.

Full working example

Here is the complete, copy-pasteable Mule 4 configuration implementing both the MCP Server (three enterprise tools with read/write safety and error handling) and an MCP Client orchestration flow.

1. Complete MCP Server XML (3 tools + validation + error handling)

src/main/mule/mcp-commerce-server.xml 
<?xml version="1.0" encoding="UTF-8"?>
<mule xmlns="http://www.mulesoft.org/schema/mule/core"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xmlns:http="http://www.mulesoft.org/schema/mule/http"
      xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core"
      xmlns:mcp="http://www.mulesoft.org/schema/mule/mcp"
      xsi:schemaLocation="
        http://www.mulesoft.org/schema/mule/core http://www.mulesoft.org/schema/mule/core/current/mule.xsd
        http://www.mulesoft.org/schema/mule/http http://www.mulesoft.org/schema/mule/http/current/mule-http.xsd
        http://www.mulesoft.org/schema/mule/ee/core http://www.mulesoft.org/schema/mule/ee/core/current/mule-ee.xsd
        http://www.mulesoft.org/schema/mule/mcp http://www.mulesoft.org/schema/mule/mcp/current/mule-mcp.xsd">

  <configuration-properties file="config/local.yaml"/>

  <http:listener-config name="HTTP_Listener_config">
    <http:listener-connection host="${http.host}" port="${http.port}"/>
  </http:listener-config>

  <http:request-config name="Orders_SAPI_Request_Config">
    <http:request-connection protocol="HTTPS" host="${sapi.orders.host}" port="${sapi.orders.port}"/>
  </http:request-config>

  <mcp:config name="Commerce_MCP_Server_Config"
              serverName="${mcp.server.name}"
              serverVersion="${mcp.server.version}">
    <mcp:streamable-http-server-connection listenerConfig="HTTP_Listener_config"
                                           mcpEndpointPath="${mcp.server.path}"/>
  </mcp:config>

  <!-- ===================================================================== -->
  <!-- TOOL 1 (READ-ONLY): lookup-order-status                               -->
  <!-- ===================================================================== -->
  <flow name="mcp-tool-lookup-order-status">
    <mcp:tool-listener config-ref="Commerce_MCP_Server_Config" name="lookup-order-status">
      <mcp:description><![CDATA[Read-only lookup of current B2B/B2C order fulfillment status, carrier tracking number, and estimated delivery date by orderId.]]></mcp:description>
      <mcp:tool-input-schema><![CDATA[{
        "$schema": "https://json-schema.org/draft/2020-12/schema",
        "type": "object",
        "required": ["orderId"],
        "additionalProperties": false,
        "properties": {
          "orderId": {
            "type": "string",
            "pattern": "^SO-[0-9]{7}$",
            "description": "Sales order identifier formatted as SO- followed by 7 digits, e.g., SO-8849201."
          }
        }
      }]]></mcp:tool-input-schema>
      <mcp:responses>
        <mcp:text-tool-response-content text="#[payload]"/>
      </mcp:responses>
    </mcp:tool-listener>

    <set-variable variableName="orderId" value="#[payload.arguments.orderId]"/>

    <http:request method="GET"
                  config-ref="Orders_SAPI_Request_Config"
                  path="/api/v1/orders/{orderId}"
                  responseTimeout="${sapi.orders.responseTimeoutMs}">
      <http:uri-params>#[{ orderId: vars.orderId }]</http:uri-params>
    </http:request>

    <ee:transform>
      <ee:message>
        <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
write({
  orderId: payload.orderNumber,
  fulfillmentStatus: payload.status,
  carrier: payload.shipment.carrierCode default "UNASSIGNED",
  trackingNumber: payload.shipment.trackingNumber,
  estimatedDeliveryDate: payload.shipment.etaIsoDate,
  totalOrderUsd: payload.financials.grossAmountUsd
}, "application/json")]]></ee:set-payload>
      </ee:message>
    </ee:transform>

    <error-handler ref="Global_MCP_Tool_Error_Handler"/>
  </flow>

  <!-- ===================================================================== -->
  <!-- TOOL 2 (READ-ONLY): check-inventory-stock                             -->
  <!-- ===================================================================== -->
  <flow name="mcp-tool-check-inventory-stock">
    <mcp:tool-listener config-ref="Commerce_MCP_Server_Config" name="check-inventory-stock">
      <mcp:description><![CDATA[Read-only real-time available-to-promise (ATP) inventory check by SKU and regional distribution center.]]></mcp:description>
      <mcp:tool-input-schema><![CDATA[{
        "$schema": "https://json-schema.org/draft/2020-12/schema",
        "type": "object",
        "required": ["sku", "region"],
        "additionalProperties": false,
        "properties": {
          "sku": {
            "type": "string",
            "pattern": "^SKU-[A-Z0-9-]{4,16}$",
            "description": "Catalog SKU code, e.g., SKU-COLD-440."
          },
          "region": {
            "type": "string",
            "enum": ["US-EAST", "US-WEST", "EU-CENTRAL", "APAC-SG"],
            "description": "Distribution warehouse region."
          }
        }
      }]]></mcp:tool-input-schema>
      <mcp:responses>
        <mcp:text-tool-response-content text="#[payload]"/>
      </mcp:responses>
    </mcp:tool-listener>

    <http:request method="GET"
                  config-ref="Orders_SAPI_Request_Config"
                  path="/api/v1/inventory/atp"
                  responseTimeout="${sapi.orders.responseTimeoutMs}">
      <http:query-params>#[{
        sku: payload.arguments.sku,
        region: payload.arguments.region
      }]</http:query-params>
    </http:request>

    <ee:transform>
      <ee:message>
        <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
write({
  sku: payload.sku,
  region: payload.warehouseRegion,
  availableToPromiseUnits: payload.atpQty,
  reservedUnits: payload.reservedQty,
  nextRestockDate: payload.nextReplenishmentDate
}, "application/json")]]></ee:set-payload>
      </ee:message>
    </ee:transform>

    <error-handler ref="Global_MCP_Tool_Error_Handler"/>
  </flow>

  <!-- ===================================================================== -->
  <!-- TOOL 3 (WRITE / STATE-MUTATING): create-return-rma                    -->
  <!-- ===================================================================== -->
  <flow name="mcp-tool-create-return-rma">
    <mcp:tool-listener config-ref="Commerce_MCP_Server_Config" name="create-return-rma">
      <mcp:description><![CDATA[Write operation: creates a Return Merchandise Authorization (RMA) for a delivered order. Requires explicit customer confirmation, reason code, and idempotencyKey. Auto-creation capped at $1,500 USD.]]></mcp:description>
      <mcp:tool-input-schema><![CDATA[{
        "$schema": "https://json-schema.org/draft/2020-12/schema",
        "type": "object",
        "required": ["orderId", "sku", "quantity", "reasonCode", "estimatedValueUsd", "idempotencyKey"],
        "additionalProperties": false,
        "properties": {
          "orderId": { "type": "string", "pattern": "^SO-[0-9]{7}$" },
          "sku": { "type": "string", "pattern": "^SKU-[A-Z0-9-]{4,16}$" },
          "quantity": { "type": "integer", "minimum": 1, "maximum": 50 },
          "reasonCode": {
            "type": "string",
            "enum": ["DAMAGED_IN_TRANSIT", "WRONG_ITEM_SHIPPED", "DEFECTIVE_UNIT"]
          },
          "estimatedValueUsd": { "type": "number", "minimum": 0.01 },
          "idempotencyKey": {
            "type": "string",
            "minLength": 12,
            "description": "Unique caller idempotency key preventing duplicate RMA creation on retry."
          }
        }
      }]]></mcp:tool-input-schema>
      <mcp:responses>
        <mcp:text-tool-response-content text="#[payload]"/>
      </mcp:responses>
    </mcp:tool-listener>

    <set-variable variableName="args" value="#[payload.arguments]"/>

    <choice>
      <when expression="#[vars.args.estimatedValueUsd > (p('sapi.rma.maxAutoRmaValueUsd') as Number)]">
        <raise-error type="APP:RMA_LIMIT_EXCEEDED"
                     description="RMA exceeds $1,500.00 autonomous agent threshold; escalate to human supervisor queue."/>
      </when>
    </choice>

    <http:request method="POST"
                  config-ref="Orders_SAPI_Request_Config"
                  path="/api/v1/returns/rma"
                  responseTimeout="${sapi.orders.responseTimeoutMs}">
      <http:body><![CDATA[#[%dw 2.0
output application/json
---
{
  orderNumber: vars.args.orderId,
  lineItemSku: vars.args.sku,
  returnQuantity: vars.args.quantity,
  reason: vars.args.reasonCode
}]]]></http:body>
      <http:headers>#[{ "Idempotency-Key": vars.args.idempotencyKey }]</http:headers>
    </http:request>

    <ee:transform>
      <ee:message>
        <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
write({
  rmaNumber: payload.rmaId,
  status: payload.rmaStatus,
  prepaidReturnLabelUrl: payload.returnLabelUrl,
  restockingFeeUsd: 0.00
}, "application/json")]]></ee:set-payload>
      </ee:message>
    </ee:transform>

    <error-handler ref="Global_MCP_Tool_Error_Handler"/>
  </flow>

  <!-- ===================================================================== -->
  <!-- SHARED ERROR HANDLER FOR MCP TOOLS                                    -->
  <!-- ===================================================================== -->
  <error-handler name="Global_MCP_Tool_Error_Handler">
    <on-error-propagate type="MCP:INVALID_ARGUMENTS">
      <logger level="WARN" message="#['MCP schema validation rejected tool call: ' ++ (error.description default '')]"/>
    </on-error-propagate>

    <on-error-continue type="HTTP:TIMEOUT, HTTP:CONNECTIVITY, APP:RMA_LIMIT_EXCEEDED">
      <ee:transform>
        <ee:message>
          <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
write({
  isError: true,
  errorCode: error.errorType.namespace ++ ":" ++ error.errorType.identifier,
  retryable: (error.errorType.identifier == "TIMEOUT"),
  guidanceForAgent: error.description
}, "application/json")]]></ee:set-payload>
        </ee:message>
      </ee:transform>
    </on-error-continue>
  </error-handler>
</mule>

2. Mule 4 MCP Client flow (discovering & calling an external MCP server)

When a Mule 4 orchestration flow acts as an MCP client—for example, querying an external freight carrier MCP server—configure <mcp:client-config> and invoke <mcp:list-tools> or <mcp:call-tool>:

src/main/mule/mcp-carrier-client.xml 
<?xml version="1.0" encoding="UTF-8"?>
<mule xmlns="http://www.mulesoft.org/schema/mule/core"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xmlns:http="http://www.mulesoft.org/schema/mule/http"
      xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core"
      xmlns:mcp="http://www.mulesoft.org/schema/mule/mcp"
      xsi:schemaLocation="
        http://www.mulesoft.org/schema/mule/core http://www.mulesoft.org/schema/mule/core/current/mule.xsd
        http://www.mulesoft.org/schema/mule/http http://www.mulesoft.org/schema/mule/http/current/mule-http.xsd
        http://www.mulesoft.org/schema/mule/ee/core http://www.mulesoft.org/schema/mule/ee/core/current/mule-ee.xsd
        http://www.mulesoft.org/schema/mule/mcp http://www.mulesoft.org/schema/mule/mcp/current/mule-mcp.xsd">

  <mcp:client-config name="External_Carrier_MCP_Client">
    <mcp:streamable-http-client-connection serverUrl="${mcp.client.externalShippingMcpUrl}"
                                           requestTimeout="${mcp.client.requestTimeoutMs}">
      <mcp:default-headers>
        <mcp:default-header key="Authorization" value="#['Bearer ' ++ p('secure::carrier.mcp.token')]"/>
      </mcp:default-headers>
    </mcp:streamable-http-client-connection>
  </mcp:client-config>

  <flow name="orchestrate-carrier-quote-via-mcp-client">
    <http:listener config-ref="HTTP_Listener_config" path="/api/v1/shipping-quote" allowedMethods="POST"/>

    <!-- Optional discovery: verify remote server capabilities -->
    <mcp:list-tools config-ref="External_Carrier_MCP_Client" target="remoteTools"/>

    <!-- Invoke remote MCP tool with strongly typed DataWeave arguments -->
    <mcp:call-tool config-ref="External_Carrier_MCP_Client" toolName="calculate-coldchain-freight">
      <mcp:arguments><![CDATA[#[%dw 2.0
output application/java
---
{
  originZip: payload.originZip,
  destinationZip: payload.destinationZip,
  palletCount: payload.pallets,
  temperatureCelsius: 4
}]]]></mcp:arguments>
    </mcp:call-tool>

    <ee:transform>
      <ee:message>
        <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
{
  availableToolCount: sizeOf(vars.remoteTools),
  isToolError: payload.isError default false,
  quoteResult: read(payload.content[0].text, "application/json")
}]]></ee:set-payload>
      </ee:message>
    </ee:transform>
  </flow>
</mule>

Run the Mule application locally (mvn clean package mule:run) and verify all three protocol layers: interactive visual testing with MCP Inspector, raw JSON-RPC 2.0 wire verification via curl, and IDE host integration.

Launch the official MCP Inspector, select Streamable HTTP transport in the left sidebar, enter http://localhost:8081/mcp, and click Connect:

2. Raw JSON-RPC 2.0 handshake, discovery, and tool call via curl

First, send initialize and capture the Mcp-Session-Id response header:

1-initialize.sh 
curl -i -sS -X POST "http://localhost:8081/mcp" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
      "protocolVersion": "2025-03-26",
      "capabilities": {},
      "clientInfo": { "name": "curl-smoke-test", "version": "1.0.0" }
    }
  }'

Next, list registered tools (tools/list) and invoke lookup-order-status (tools/call) passing the returned session header:

2-list-and-call-tool.sh 
# Discover tools
curl -sS -X POST "http://localhost:8081/mcp" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: 9b2e4f10-8a7c-4d11-9312-77c04e19a001" \
  -d '{ "jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {} }' | jq .

Deploy to production

  • CloudHub 2.0 Ingress & HTTP timeouts: Set the CloudHub 2.0 Ingress response timeout to at least 60s if any downstream ERP/WMS orchestration aggregates multiple System APIs, while keeping individual http:request timeouts strictly bounded (5000ms) so slow backends fail fast with actionable guidance to the LLM.
  • Worker / Replica sizing: For 3–15 MCP tools handling 50 RPS of tool calls, deploy 2 replicas × 0.2 vCore (or 0.5 vCore when executing heavy DataWeave payload transformations) on Java 17 and Mule 4.9 LTS.
  • Catalog in Anypoint Exchange Agent Registry: Publish the deployed /mcp endpoint as an mcp-server asset in Exchange so MuleSoft Agent Fabric Brokers and partner teams can discover its versioned tool schemas automatically.
  • Dedicated health endpoint: Add a lightweight GET /health flow on the same HTTP_Listener_config returning 200 OK for Kubernetes/RTF readiness probes (probes must not call POST /mcp without JSON-RPC framing).

Security & governance

Design coarse-grained business tools, not thin CRUD wrappers

Never expose generic SQL/SOQL pass-through or unrestricted DELETE endpoints as MCP tools. Bind every write tool to strict enum reason codes, numeric value caps, and mandatory caller idempotency keys.

  • OAuth 2.0 JWT + tool-level authorization: Enforce JWT validation on /mcp via Flex Gateway, and inspect attributes.headers['authorization'] claims when routing sensitive write tools like create-return-rma.
  • mTLS between Flex Gateway and Mule replicas: Terminate public TLS at Flex Gateway or CloudHub 2.0 Private Space ingress and enforce mTLS on upstream connections to the Mule container.
  • Output sanitization against indirect prompt injection: Free-text fields stored in CRM/ERP databases (such as customer delivery notes) can contain adversarial prompt-injection strings. Strip control directives and cap free-text field lengths in DataWeave before returning <mcp:text-tool-response-content>.
  • JSON-RPC method allowlisting: Restrict external callers at Flex Gateway if needed so untrusted clients can only invoke initialize, notifications/initialized, ping, tools/list, and tools/call.

Production checklist

  • Compiled on JDK 17 + Mule 4.9 LTS using com.mulesoft.connectors:mule-mcp-connector:1.2.0 (mule-plugin).
  • Streamable HTTP configured on /mcp (legacy dual-endpoint SSE disabled unless explicitly required).
  • Every <mcp:tool-listener> includes rich domain descriptions, regex patterns, enums, and additionalProperties: false.
  • Read-only tools separated from write tools; all mutating tools enforce value thresholds and idempotency keys.
  • DataWeave projections trim downstream ERP/CRM payloads to minimal token-efficient business fields.
  • Domain errors return structured isError: true guidance via on-error-continue rather than opaque HTTP 500 stack traces.
  • Flex Gateway protects /mcp with OAuth 2.0 JWT validation, client SLA rate limits, and PII masking.
  • MUnit test suite covers schema rejection (MCP:INVALID_ARGUMENTS), RMA cap guardrail, and SAPI timeout handling.
  • MCP Server registered in Anypoint Exchange Agent Registry with owner team and SLA metadata.

Interview questions

1. Why does MuleSoft recommend Streamable HTTP over the older HTTP+SSE MCP transport for CloudHub 2.0 and Runtime Fabric?

Legacy HTTP+SSE required opening a persistent GET /sse connection on one Mule replica and sending subsequent POST /message calls to that exact same replica's in-memory session state—which breaks across stateless L7 load balancers without sticky session pinning and gets dropped by enterprise firewalls. Streamable HTTP unifies request/response and optional streaming onto a single /mcp endpoint with explicit Mcp-Session-Id headers, enabling clean horizontal scaling and standard API gateway policy enforcement.

2. How should error handling inside an <mcp:tool-listener> flow differ from a traditional REST System API?

In a REST API, returning HTTP 422 or HTTP 504 expects deterministic code to parse status codes. In MCP, unhandled transport 500s often crash or blind the agent run. Instead, let protocol/schema violations propagate as JSON-RPC MCP:INVALID_ARGUMENTS (-32602), while catching recoverable business rule rejections or upstream timeouts in on-error-continue and returning a structured payload with isError: true, retryable boolean, and plain-language guidanceForAgent so the LLM can self-correct or escalate gracefully.

3. Why shouldn't you auto-expose every System API endpoint 1:1 as an MCP tool?

LLMs degrade rapidly in tool-selection accuracy once exposed to 30+ fine-grained CRUD endpoints with overlapping names and complex join requirements, while each extra chained tool call adds 1–3 seconds of LLM reasoning latency and thousands of tokens. Best practice in Mule 4 is designing coarse-grained, task-oriented MCP tools (like Process APIs) that orchestrate multiple System API calls and DataWeave joins internally in milliseconds.

4. How do you protect state-mutating MCP tools (like create-return-rma) from duplicate execution and over-privileged actions?

Combine four controls: (1) require a caller-generated idempotencyKey in the JSON Schema backed by Object Store v2 deduplication, (2) enforce deterministic Mule <choice> guardrails (e.g., rejecting RMAs above $1,500 before calling the ERP), (3) propagate user-scoped OAuth 2.0 JWTs rather than static admin credentials, and (4) require human-in-the-loop confirmation in the upstream Agent Broker for irreversible writes.

5. When would a Mule 4 application use <mcp:client-config> and <mcp:call-tool> instead of a standard HTTP Request connector?

Use the MCP Client operations whenever Mule orchestrates capabilities exposed by internal or partner MCP servers—such as dynamic tool catalogs discovered at runtime via <mcp:list-tools>, SaaS vendor MCP endpoints, or domain MCP servers cataloged in Agent Fabric. The connector handles JSON-RPC 2.0 session initialization, Mcp-Session-Id lifecycle, protocol version negotiation, and content-block parsing automatically.
