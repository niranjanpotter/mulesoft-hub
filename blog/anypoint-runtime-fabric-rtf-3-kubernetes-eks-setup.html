Anypoint Runtime Fabric (RTF 3.x) on Kubernetes (EKS/AKS): Setup, restartGeneration & Zero-Downtime Upgrades

Deploy and run Anypoint Runtime Fabric 3.x (v3.0.41102) on EKS or AKS: configure rtfctl, Helm, local registries, K8s 1.30-1.37 alignment, and declarative spec.lifecycle.restartGeneration rolling restarts.

⚡ Quick Answer

Anypoint Runtime Fabric (RTF) 3.x deploys Mule 4.9 LTS and 4.13 Edge workloads natively onto self-managed Kubernetes clusters (AWS EKS, Azure AKS, OpenShift, K8s 1.30-1.37). The November 19, 2026 release (v3.0.41102) bundles updated rtf-agent (3.0.41102), rtf-core-actions (1.0.10500), and rtf-cluster-ops (2.0), plus declarative rolling restarts via `spec.lifecycle.restartGeneration` so GitOps pipelines trigger zero-downtime pod recycles cleanly.

CloudHub 2.0 vs. Runtime Fabric (RTF 3.x) — Choosing the Right Deployment Model

Both CloudHub 2.0 and RTF 3.x run containerized Mule workloads on Kubernetes under identical Mule Maven Plugin deployment concepts, yet serve different infrastructure priorities:

DimensionCloudHub 2.0 (MuleSoft-Managed)Runtime Fabric 3.x (Customer K8s)
Control plane & patchingManaged by MuleSoftCustomer owns EKS/AKS cluster + Ingress; Anypoint manages Mule pods via rtf-agent
Data residency / On-prem ERPCloud Private Spaces via VPN/Transit GWDeploy directly inside on-prem DC or strict regulated local VPCs
CPU bursting & sizingFixed vCore tiersFine-grained Kubernetes mCPU reserved vs burst limit controls

Zero-downtime secret rotation & restarts with restartGeneration

Prior to recent RTF controller improvements, restarting a Mule application to pick up rotated Kubernetes Secrets or refreshed external keystore volumes required imperative kubectl rollout restart scripts outside Anypoint. With declarative spec.lifecycle.restartGeneration, bumping the integer in ArgoCD/Flux triggers one clean rolling restart managed natively by the Anypoint Controller.

Frequently Asked Questions & Interview Q&A

What does Anypoint Runtime Fabric 3.0.41102 (Nov 2026) introduce?

RTF 3.0.41102 updates bundled container components (rtf-agent:3.0.41102, rtf-core-actions:1.0.10500, rtf-cluster-ops:2.0) with security vulnerability fixes and supports declarative rolling restarts via `spec.lifecycle.restartGeneration` cleanly on EKS/AKS.

How does `spec.lifecycle.restartGeneration` work on Runtime Fabric?

Incrementing the integer value under `spec.lifecycle.restartGeneration` on your MuleApplication manifest signals the Anypoint Controller to execute one declarative rolling restart of the application pods without downtime.

What is the difference between CPU Reserved and CPU Limit in RTF deployment settings?

CPU Reserved guarantees minimum node compute capacity scheduled for the pod (which drives licensing/bin-packing), while CPU Limit allows the JVM to burst higher during initial application startup and traffic spikes.

Why must replicas be set >= 2 with enforceDeployingReplicasAcrossNodes?

Running 2+ replicas spread across separate Kubernetes worker nodes guarantees high availability during node OS upgrades, spot instance drains, or rolling deployments.

How do Kubernetes minor version upgrades affect Runtime Fabric?

RTF maintains certified Kubernetes version support windows (covering K8s 1.30 through 1.37 alignment). Always check the MuleSoft RTF support matrix and upgrade rtf-agent cleanly before bumping EKS/AKS control plane versions.
