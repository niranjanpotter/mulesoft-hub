⚡ Quick Answer

Mule 4.13.0 Edge (Oct 2026) and patch 4.13.2 (Nov 2026) bundle DataWeave 2.13.0/2.13.1 on Java 17, introducing native JWT signing via dw::util::jwt::HMAC and dw::util::jwt::RSA (no external Exchange library needed) and enforcing JDK 17+ JPMS filtering so unexported Java packages throw IllegalAccessException unless explicitly opened or refactored.

1. dw::util::jwt::HMAC vs dw::util::jwt::RSA in DataWeave 2.13

Before DataWeave 2.13 (Oct 2026), generating signed JWTs in MuleSoft required custom Java classes (jjwt/nimbus-jose-jwt) or external Exchange modules. Now both symmetric (HMAC) and asymmetric (RSA) signing are built straight into DataWeave:

  • dw::util::jwt::HMAC: Supports HS256, HS384, and HS512 with a shared secret string.
  • dw::util::jwt::RSA: Supports RS256 (Sha256withRSA), RS384 (Sha384withRSA), and RS512 with unencrypted PKCS#1 or PKCS#8 PEM private keys.
%dw 2.0
output application/json
import * from dw::util::jwt::HMAC
---
{
  jwt: JWT({alg: "HS256", typ: "JWT"}, {sub: "partner-01", exp: 1796000000}, Mule::p('secure::jwt.hmacSecret'), "HmacSHA256")
}

2. Fixing JDK 17 JPMS IllegalAccessException When Upgrading to 4.13

Mule 4.13.0 + DataWeave 2.13.0 tightens Java Platform Module System (JPMS) reflection security on JDK 17+. Unexported JDK packages are now filtered out during Java module resolution inside DataWeave. Any legacy script calling internal JDK helpers (e.g., sun.misc.* or non-public java.util.* internals) will fail cleanly at resolution time rather than slipping through with warnings.

Rule of thumb (and MuleGuard check): Audit every java! import in `.dwl` files and custom Java SDK classes before bumping app.runtime to 4.13.2.

Frequently Asked Questions & Interview Q&A

Do I still need an external Java library to sign JWTs in Mule 4.13?

No. DataWeave 2.13.0 (bundled with Mule 4.13.0+) includes native dw::util::jwt::HMAC and dw::util::jwt::RSA modules supporting HS256/384/512 and RS256/384/512.

Why did my Java call inside DataWeave break after upgrading to Mule 4.13?

DataWeave 2.13.0 enforces JDK 17+ JPMS package filtering by default, blocking access to unexported internal JDK packages. Replace internal calls with exported public Java 17 APIs.

What else improved in Mule 4.13.2 / DataWeave 2.13.1?

November 2026 patch releases lowered memory consumption for text/plain DataWeave outputs, upgraded Jackson to 2.21.7, and improved Java map thread safety.
