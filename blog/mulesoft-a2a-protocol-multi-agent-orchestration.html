Agent-to-Agent (A2A) Protocol in MuleSoft: Agent Cards, Delegation & Multi-Cloud Orchestration

Implement horizontal peer-to-peer agent delegation across Salesforce Agentforce, AWS Bedrock, Google Vertex AI, and MuleSoft using the official Mule 4 A2A Connector (mule4-a2a-connector:2.0.0), standardized Agent Cards, and stateful JSON-RPC task lifecycles.

TL;DR

  • MCP is vertical; A2A is horizontal: Model Context Protocol (MCP) connects an agent vertically to deterministic tools and data; Agent-to-Agent (A2A) connects autonomous, opaque peer agents horizontally so a coordinator can delegate open-ended goals without seeing a specialist's private prompts, memory, or internal tools.
  • Official Mule 4 A2A Connector: Add com.mulesoft.connectors:mule4-a2a-connector:2.0.0 (<classifier>mule-plugin</classifier>) with XML namespace http://www.mulesoft.org/schema/mule/a2a to expose any Mule 4 app as an A2A Server or orchestrate remote A2A peers as an A2A Client.
  • CloudHub-safe Agent Cards: Always reference your Agent Card via file="${app.home}/agent-card.json" (placed in src/main/resources/agent-card.json)—hardcoding workstation paths breaks immediately inside CloudHub 2.0 Linux containers.
  • Rich asynchronous task state machine: Unlike synchronous REST calls, A2A models long-running, multi-turn work across submitted, working, input-required, completed, failed, and canceled states, returning typed artifacts correlated by sessionId and taskId.
  • MuleSoft as the Enterprise Agent Control Plane: Placing Anypoint Flex Gateway and MuleSoft A2A coordinators between Agentforce, Bedrock, Vertex AI, and LangGraph enforces unified OAuth 2.0 identity, budget circuit breakers, and cross-cloud audit trails.

Real Anypoint View

What it is and why it matters

No single enterprise runs on one AI vendor. Your CRM customer-service copilot lives in Salesforce Agentforce, your fraud-detection reasoning agent runs on AWS Bedrock, your supply-chain carrier optimizer runs on Google Vertex AI, and your back-office ERP dispute specialist runs in MuleSoft or Python LangGraph. Without an open wire protocol, connecting two agents forces engineers to write brittle custom REST wrappers that flatten multi-turn conversations, lose streaming progress, and leak internal prompt structures.

The Agent-to-Agent (A2A) Protocol establishes an open HTTP + JSON-RPC 2.0 + Server-Sent Events (SSE) standard for opaque peer collaboration. Every compliant agent publishes a machine-readable discovery manifest at GET /.well-known/agent.json (its Agent Card) advertising its skills, input/output modalities, streaming support, and OAuth schemes—while keeping its internal chain-of-thought, RAG vector stores, and downstream MCP tools completely encapsulated.

MCP vs. A2A: Complementary Layers, Not Competitors

Architects are frequently asked in design reviews: "If we already standardized on MCP, why do we need A2A?" Because they operate at fundamentally different layers of the agentic stack:

Architectural Axis MCP (Agent-to-Tool / Data — Vertical) A2A (Agent-to-Agent — Horizontal)
Target abstraction Deterministic functions, APIs, database queries, and static resources with fixed JSON Schema inputs. Autonomous peer specialist agents capable of planning, reasoning, and asking clarifying questions.
Opacity & state White-box signature: caller picks exact tool arguments; calls are typically short-lived and stateless. Black-box execution: caller delegates a natural-language/structured goal; specialist owns private state and tools.
Interaction lifecycle Single request/response (tools/call → result). Stateful task machine (submitted → working → input-required → completed) + async webhooks.
Discovery mechanism tools/list, resources/list, prompts/list over MCP session. GET /.well-known/agent.json (Agent Card) + Enterprise Agent Registry / Anypoint Exchange.
How they work together A Dispute Specialist Agent uses MCP internally to query SAP invoices and Stripe chargebacks. An Agentforce Triage Agent uses A2A to delegate the entire dispute case to that Dispute Specialist Agent.

Understanding the A2A Task State Machine

Every A2A delegation revolves around a uniquely addressable Task (taskId) grouped within an optional conversation thread (sessionId):

  • submitted: Task accepted and persisted by the specialist agent, queued for execution.
  • working: Specialist is actively reasoning, invoking internal MCP tools, or awaiting downstream ERP systems.
  • input-required: Specialist lacks critical context (e.g., missing damage photo receipt ID or customer confirmation on a partial refund) and yields control back to the caller to supply another turn under the same taskId.
  • completed: Goal achieved; final structured JSON or markdown deliverables are attached in the artifacts array.
  • failed / canceled: Terminal states reached on unrecoverable domain errors or explicit caller cancellation (tasks/cancel).

Architecture

In the reference multi-cloud topology below, a customer contacts an Agentforce Concierge about a damaged high-value shipment and duplicate billing charge. Agentforce delegates the case over A2A to a MuleSoft A2A Triage Coordinator, which fans out specialized sub-tasks to an Order Dispute Specialist Agent (MuleSoft A2A Server) and a Fraud Risk Agent (AWS Bedrock), while the Dispute Specialist uses MCP internally to inspect SAP and Stripe.

Prerequisites

You need
  • Java 17 and Mule Runtime 4.9.0+ (Anypoint Code Builder or Anypoint Studio 7.21+).
  • Anypoint Enterprise Maven Repository credentials configured in ~/.m2/settings.xml to resolve com.mulesoft.connectors:mule4-a2a-connector:2.0.0.
  • OAuth 2.0 Identity Provider issuing Bearer JWTs for agent-to-agent client authentication and user context delegation.
  • Object Store v2 enabled (for CloudHub 2.0 deployments) to persist stateful taskId and sessionId transitions across worker replicas.

Step-by-step setup

  1. Add the official MuleSoft A2A Connector 2.0.0 to pom.xml

    Declare mule4-a2a-connector version 2.0.0 alongside the HTTP and ObjectStore connectors so your Mule app can host A2A endpoints and persist multi-turn task state.

    pom.xml 
    <dependency>
  <groupId>com.mulesoft.connectors</groupId>
  <artifactId>mule4-a2a-connector</artifactId>
  <version>2.0.0</version>
  <classifier>mule-plugin</classifier>
</dependency>
<dependency>
  <groupId>org.mule.connectors</groupId>
  <artifactId>mule-http-connector</artifactId>
  <version>1.10.3</version>
  <classifier>mule-plugin</classifier>
</dependency>
<dependency>
  <groupId>org.mule.connectors</groupId>
  <artifactId>mule-objectstore-connector</artifactId>
  <version>1.2.2</version>
  <classifier>mule-plugin</classifier>
</dependency>
  2. Author src/main/resources/agent-card.json

    Place your Agent Card inside src/main/resources/agent-card.json. The A2A Connector automatically serves this JSON document at GET /.well-known/agent.json so remote orchestrators can inspect your agent's capabilities, authentication requirements, and domain skills dynamically.

  "url": "https://dispute-agent.acme-corp.com/",
  "provider": {
    "organization": "Acme Corp Integration Platform",
    "url": "https://acme-corp.com"
  },
  "version": "2.1.0",
  "documentationUrl": "https://anypoint.mulesoft.com/exchange/acme/order-dispute-a2a-agent/",

    "streaming": true,
    "pushNotifications": false,
    "stateTransitionHistory": true
  },
  "authentication": {
    "schemes": ["OAuth2", "Bearer"],
    "credentials": "Requires OAuth 2.0 Bearer JWT with audience api://acme-dispute-a2a and scope a2a:disputes:delegate"
  },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json", "text/markdown"],
  "skills": [
    {
      "id": "investigate_billing_or_damage_dispute",
      "name": "Investigate Order Dispute & Issue Credit",
      "description": "Reconciles order invoice, carrier proof-of-delivery, and payment capture to adjudicate duplicate-charge or damaged-transit claims.",
      "tags": ["orders", "disputes", "refunds", "chargebacks", "sap", "stripe"],

      ]
    }
  ]
}
  3. Configure <a2a:server-config> using ${app.home}/agent-card.json

    Bind the A2A Server configuration to your shared HTTP_Listener_config and point <a2a:agent-card> to ${app.home}/agent-card.json.

    Critical CloudHub 2.0 Deployment Rule: Always use ${app.home}

    Never use a workstation path like D:/projects/src/main/resources/agent-card.json or bare relative src/main/resources/agent-card.json. During mvn package, Maven copies everything under src/main/resources/ to the root of your deployable JAR, which CloudHub 2.0 and Runtime Fabric unpack into /opt/mule/apps/<app-name>/—resolved at runtime exclusively via ${app.home}/agent-card.json.

    Mule XML — A2A Server Configuration 
    <a2a:server-config name="A2A_Server_config">
  <a2a:connection listenerConfig="HTTP_Listener_config" agentPath="/"/>
  <a2a:agent-card file="${app.home}/agent-card.json"/>
</a2a:server-config>
  4. Implement stateful task listeners and multi-turn input-required handling

    Inside your specialist Mule flow, inspect the incoming A2A message parts. If an order number or damage evidence reference is missing for claims over $250, return task state input-required with a prompt explaining exactly what the coordinator must ask the customer; otherwise execute the investigation and emit a typed JSON artifact with state completed.

Full working example

Here are both halves of a complete production A2A implementation in Mule 4: first, the Order Dispute Specialist A2A Server; second, the Multi-Cloud Triage A2A Coordinator Client that delegates tasks across MuleSoft and AWS Bedrock agents.

1. A2A Specialist Server (order-dispute-a2a-agent.xml)

src/main/mule/order-dispute-a2a-agent.xml 
<?xml version="1.0" encoding="UTF-8"?>
<mule xmlns="http://www.mulesoft.org/schema/mule/core"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xmlns:http="http://www.mulesoft.org/schema/mule/http"
      xmlns:a2a="http://www.mulesoft.org/schema/mule/a2a"
      xmlns:os="http://www.mulesoft.org/schema/mule/os"
      xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core"
      xsi:schemaLocation="
        http://www.mulesoft.org/schema/mule/core http://www.mulesoft.org/schema/mule/core/current/mule.xsd
        http://www.mulesoft.org/schema/mule/http http://www.mulesoft.org/schema/mule/http/current/mule-http.xsd
        http://www.mulesoft.org/schema/mule/a2a http://www.mulesoft.org/schema/mule/a2a/current/mule-a2a.xsd
        http://www.mulesoft.org/schema/mule/os http://www.mulesoft.org/schema/mule/os/current/mule-os.xsd
        http://www.mulesoft.org/schema/mule/ee/core http://www.mulesoft.org/schema/mule/ee/core/current/mule-ee.xsd">

  <http:listener-config name="HTTP_Listener_config">
    <http:listener-connection host="0.0.0.0" port="${https.port}"/>
  </http:listener-config>

  <a2a:server-config name="A2A_Server_config">
    <a2a:connection listenerConfig="HTTP_Listener_config" agentPath="/"/>
    <a2a:agent-card file="${app.home}/agent-card.json"/>
  </a2a:server-config>

  <os:object-store name="Dispute_Task_Store"
                   persistent="true"
                   entryTtl="24"
                   entryTtlUnit="HOURS"
                   maxEntries="10000"/>

  <flow name="a2a-dispute-task-handler-flow">
    <a2a:task-listener config-ref="A2A_Server_config"/>

    <ee:transform doc:name="Extract Task Context & Entities">
      <ee:variables>
        <ee:set-variable variableName="taskCtx"><![CDATA[%dw 2.0
output application/java
var rawText = (payload.message.parts filter ($.type == "text") map $.text) joinBy " "
var dataPart = (payload.message.parts filter ($.type == "data"))[0].data default {}
var matchedOrd = (rawText scan /ORD-[0-9]{6}/)[0][0] default dataPart.orderNumber
var matchedEvd = (rawText scan /EVD-[0-9]{5}/)[0][0] default dataPart.evidenceReceiptId
---
{
  taskId: payload.id,
  sessionId: payload.sessionId default uuid(),
  orderNumber: matchedOrd,
  evidenceReceiptId: matchedEvd,
  claimType: dataPart.claimType default (if (lower(rawText) contains "damaged") "DAMAGED" else "DUPLICATE_CHARGE")
}]]></ee:set-variable>
      </ee:variables>
    </ee:transform>

    <os:retrieve key="#[vars.taskCtx.taskId]" objectStore="Dispute_Task_Store" target="priorState">
      <os:default-value><![CDATA[#[{}]]]></os:default-value>
    </os:retrieve>

    <ee:transform doc:name="Merge Multi-Turn Task State">
      <ee:variables>
        <ee:set-variable variableName="mergedCtx"><![CDATA[%dw 2.0
output application/java
---
{
  taskId: vars.taskCtx.taskId,
  sessionId: vars.taskCtx.sessionId,
  orderNumber: vars.taskCtx.orderNumber default vars.priorState.orderNumber,
  evidenceReceiptId: vars.taskCtx.evidenceReceiptId default vars.priorState.evidenceReceiptId,
  claimType: vars.taskCtx.claimType default vars.priorState.claimType
}]]></ee:set-variable>
      </ee:variables>
    </ee:transform>

    <choice doc:name="Check Required Investigation Inputs">
      <when expression="#[isEmpty(vars.mergedCtx.orderNumber) or (vars.mergedCtx.claimType == 'DAMAGED' and isEmpty(vars.mergedCtx.evidenceReceiptId))]">
        <os:store key="#[vars.mergedCtx.taskId]" objectStore="Dispute_Task_Store">
          <os:value><![CDATA[#[vars.mergedCtx]]]></os:value>
        </os:store>
        <ee:transform doc:name="Build input-required A2A Response">
          <ee:message>
            <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
{
  id: vars.mergedCtx.taskId,
  sessionId: vars.mergedCtx.sessionId,
  status: {
    state: "input-required",
    timestamp: now() as String {format: "yyyy-MM-dd'T'HH:mm:ss'Z'"},
    message: {
      role: "agent",
      parts: [
        {
          "type": "text",
          text: if (isEmpty(vars.mergedCtx.orderNumber))
            "Please provide the 6-digit order number formatted as ORD-XXXXXX."
          else
            "For damaged-transit claims on " ++ vars.mergedCtx.orderNumber ++ ", please provide the photo evidence receipt ID (EVD-XXXXX)."
        }
      ]
    }
  }
}]]></ee:set-payload>
          </ee:message>
        </ee:transform>
      </when>

      <otherwise>
        <!-- Internal SAP Invoice + Stripe Chargeback Reconciliation Subflow -->
        <flow-ref name="reconcile-sap-and-stripe-subflow"/>
        <os:store key="#[vars.mergedCtx.taskId]" objectStore="Dispute_Task_Store">
          <os:value><![CDATA[#[vars.mergedCtx ++ {resolved: true}]]]></os:value>
        </os:store>
        <ee:transform doc:name="Build completed A2A Response with Artifacts">
          <ee:message>
            <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
{
  id: vars.mergedCtx.taskId,
  sessionId: vars.mergedCtx.sessionId,
  status: {
    state: "completed",
    timestamp: now() as String {format: "yyyy-MM-dd'T'HH:mm:ss'Z'"},
    message: {
      role: "agent",
      parts: [
        {
          "type": "text",
          text: "Dispute approved for " ++ vars.mergedCtx.orderNumber ++ ". Duplicate capture verified and credit memo CM-2026-8841 issued for $249.00 USD."
        }
      ]
    }
  },
  artifacts: [
    {
      name: "dispute-resolution-decision",
      description: "Audited SAP + Stripe adjudication record",
      index: 0,
      lastChunk: true,
      parts: [
        {
          "type": "data",
          data: {
            orderNumber: vars.mergedCtx.orderNumber,
            evidenceReceiptId: vars.mergedCtx.evidenceReceiptId,
            decision: "APPROVED_FULL_CREDIT",
            creditMemoId: "CM-2026-8841",
            refundAmountUsd: 249.00,
            stripeRefundId: "re_3Q9xLm2eZvKYlo2C1102"
          }
        }
      ]
    }
  ]
}]]></ee:set-payload>
          </ee:message>
        </ee:transform>
      </otherwise>
    </choice>
  </flow>

  <sub-flow name="reconcile-sap-and-stripe-subflow">
    <logger level="INFO" message="#['Reconciling SAP delivery & Stripe ledger for taskId=' ++ vars.mergedCtx.taskId ++ ' order=' ++ vars.mergedCtx.orderNumber]"/>
  </sub-flow>
</mule>

2. A2A Coordinator Client (enterprise-triage-coordinator.xml)

This coordinator flow uses <a2a:client-config> to delegate fraud scoring to an AWS Bedrock A2A peer in parallel with delegating dispute resolution to our MuleSoft Specialist Server, enforcing a hop-count header so cyclic agent delegations can never loop infinitely:

src/main/mule/enterprise-triage-coordinator.xml 
<?xml version="1.0" encoding="UTF-8"?>
<mule xmlns="http://www.mulesoft.org/schema/mule/core"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xmlns:http="http://www.mulesoft.org/schema/mule/http"
      xmlns:a2a="http://www.mulesoft.org/schema/mule/a2a"
      xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core"
      xsi:schemaLocation="
        http://www.mulesoft.org/schema/mule/core http://www.mulesoft.org/schema/mule/core/current/mule.xsd
        http://www.mulesoft.org/schema/mule/http http://www.mulesoft.org/schema/mule/http/current/mule-http.xsd
        http://www.mulesoft.org/schema/mule/a2a http://www.mulesoft.org/schema/mule/a2a/current/mule-a2a.xsd
        http://www.mulesoft.org/schema/mule/ee/core http://www.mulesoft.org/schema/mule/ee/core/current/mule-ee.xsd">

  <a2a:client-config name="Dispute_Specialist_A2A_Client">
    <a2a:client-connection agentUrl="https://dispute-agent.acme-corp.com/">
      <a2a:bearer-authentication token="#[vars.delegatedDisputeJwt]"/>
    </a2a:client-connection>
  </a2a:client-config>

  <a2a:client-config name="Bedrock_Fraud_A2A_Client">
    <a2a:client-connection agentUrl="https://fraud-agent.bedrock.acme-corp.com/">
      <a2a:bearer-authentication token="#[vars.delegatedFraudJwt]"/>
    </a2a:client-connection>
  </a2a:client-config>

  <flow name="orchestrate-customer-dispute-flow">
    <ee:transform doc:name="Enforce Hop Budget & Init Correlation">
      <ee:variables>
        <ee:set-variable variableName="hopCount"><![CDATA[%dw 2.0
output application/java
var currentHop = (attributes.headers['x-a2a-hop-count'] default "0") as Number
---
if (currentHop >= 4)
  dw::Runtime::fail("MAX_A2A_DELEGATION_HOPS_EXCEEDED")
else
  currentHop + 1]]></ee:set-variable>
        <ee:set-variable variableName="sessionId"><![CDATA[#[payload.sessionId default uuid()]]]></ee:set-variable>
      </ee:variables>
    </ee:transform>

    <scatter-gather doc:name="Parallel Multi-Cloud Peer Delegation">
      <route>
        <a2a:send-task config-ref="Bedrock_Fraud_A2A_Client" doc:name="Delegate Fraud Check (AWS Bedrock)">
          <a2a:task-payload><![CDATA[#[output application/json --- {
            id: "fraud-" ++ vars.sessionId,
            sessionId: vars.sessionId,
            message: {
              role: "user",
              parts: [{ "type": "data", data: { customerEmail: payload.customerEmail, orderNumber: payload.orderNumber } }]
            }
          }]]]></a2a:task-payload>
        </a2a:send-task>
      </route>

      <route>
        <a2a:send-task config-ref="Dispute_Specialist_A2A_Client" doc:name="Delegate Order Dispute (MuleSoft)">
          <a2a:task-payload><![CDATA[#[output application/json --- {
            id: payload.taskId default ("disp-" ++ vars.sessionId),
            sessionId: vars.sessionId,
            message: {
              role: "user",
              parts: [
                { "type": "text", text: payload.customerPrompt },
                { "type": "data", data: { orderNumber: payload.orderNumber, evidenceReceiptId: payload.evidenceReceiptId, claimType: payload.claimType } }

Deploy to production

  • Verify ${app.home}/agent-card.json packaging in CI: Add a post-package assertion (jar tf target/*.jar | grep '^agent-card.json$') so broken resource paths never reach CloudHub 2.0.
  • Externalize environment URLs inside the Agent Card: The url property in agent-card.json tells A2A clients where to send subsequent tasks/send calls—ensure Dev, Stage, and Prod ingress hostnames are templated via Maven resource filtering or served behind your environment's canonical Flex Gateway domain.
  • Use persistent Object Store v2 across multi-replica deployments: In CloudHub 2.0 with 2+ replicas, an input-required Turn 2 request will routinely land on a different worker pod than Turn 1. Backing taskId state with persistent Object Store v2 (or Redis) avoids split-brain task-not-found errors.
  • Configure SSE streaming (tasks/sendSubscribe) buffering off: When "streaming": true is enabled in your Agent Card, set X-Accel-Buffering: no and disable response buffering on ingress proxies so TaskStatusUpdateEvent and TaskArtifactUpdateEvent chunks stream in real time to Agentforce or web UIs.

Security & governance

  • Enforce Hop-Count & Cost Circuit Breakers: Multi-agent graphs can accidentally form cycles (Agent A delegates to Agent B, which delegates to Agent C, which consults Agent A). Require an X-A2A-Hop-Count header (failing hard at depth ≥ 4) and propagate a deadline timestamp (X-A2A-Deadline-Epoch-Ms) across all A2A peers.
  • Cryptographic Agent Identity + Human OBO Claims: Authenticate the calling peer agent via mTLS or OAuth client assertion while carrying the originating human user's identity inside RFC 8693 chained act claims. An HR Payroll Specialist Agent should reject A2A delegations initiated from an external Customer Support Concierge even if both run inside the same enterprise.
  • Catalog Every Agent Card in Anypoint Exchange: Register internal and third-party A2A Agent Cards as governed assets in Anypoint Exchange (via MuleSoft Agent Fabric / Topic Center) so architects maintain a live topology map of agent skills, owners, SLAs, and data classifications.
  • Treat Peer Agent Text Outputs as Untrusted Input: A compromised or prompt-injected external vendor agent can embed adversarial instructions inside its narrative status.message. Prefer structured JSON data parts validated against strict schemas when passing outputs between coordinator steps.

Production checklist

  • mule4-a2a-connector:2.0.0 configured with <a2a:agent-card file="${app.home}/agent-card.json"/> and verified inside packaged JAR root.
  • GET /.well-known/agent.json advertises accurate environment HTTPS url, capabilities, OAuth schemes, and unambiguous skills examples.
  • Multi-turn task context (taskId, sessionId, state history) stored in persistent Object Store v2 or Redis with explicit TTL cleanup.
  • Every A2A endpoint protected by Anypoint Flex Gateway enforcing OAuth 2.0 audience-restricted JWTs, per-caller rate limits, and chained act audit logging.
  • Delegation loop guards (X-A2A-Hop-Count max depth and per-request deadline propagation) enforced on all outbound <a2a:send-task> calls.
  • Structured deliverables emitted inside typed JSON artifacts rather than unstructured prose alone so upstream coordinators parse outcomes deterministically.
  • Long-running ERP or human-approval tasks (> 30 seconds) return immediate working state and stream SSE updates or push webhook notifications instead of holding blocking sockets.
  • All internal and external A2A Agent Cards registered and versioned in Anypoint Exchange for cross-team discovery and governance.

Interview questions

1. How do you explain the difference between MCP and A2A to a CIO or Enterprise Architecture board?

MCP (Model Context Protocol) is how a single agent uses tools and data—like giving a mechanic a wrench and a diagnostic scanner with exact button inputs. A2A (Agent-to-Agent Protocol) is how independent specialist agents collaborate as peers—like a service advisor handing a complex transmission rebuild ticket to a master transmission specialist. With A2A, the coordinator states the goal and context without needing visibility into the specialist's private prompts, reasoning model, or internal MCP tools—enabling clean interoperability across Salesforce Agentforce, AWS Bedrock, Vertex AI, and MuleSoft.

2. Why does referencing agent-card.json without ${app.home} work locally in Anypoint Studio/ACB on Windows or macOS but fail in CloudHub 2.0?

On a developer laptop, relative paths sometimes resolve accidentally against the IDE's working directory, and absolute paths like C:\workspace\... exist on the local disk. Inside CloudHub 2.0 or Runtime Fabric Kubernetes containers, the JVM working directory is not your project root—Mule unpacks your packaged JAR under /opt/mule/apps/<app-name>/, where src/main/resources/ files sit at the root of ${app.home}. Using file="${app.home}/agent-card.json" guarantees portable resolution across local Studio, CI MUnit runs, RTF, and CloudHub 2.0.

3. Walk through how A2A handles a multi-turn human-in-the-loop clarification mid-delegation.

When Coordinator Agent A sends tasks/send (id: "task-9041", sessionId: "sess-77") to Specialist Agent B, and Agent B discovers a required business input is missing (such as a photo receipt ID or user approval for a restocking fee), Agent B persists its partial context and responds with status.state = "input-required" plus a prompt message. Coordinator A surfaces that question to the human user, collects the answer, and invokes tasks/send again with the exact same taskId. Agent B loads prior state from Object Store, completes execution, and transitions the task to completed with final artifacts.

4. How do you prevent infinite delegation loops and runaway LLM costs in a decentralized multi-agent mesh?

Combine four controls at the MuleSoft orchestration and Flex Gateway layers: (1) inject and increment an immutable X-A2A-Hop-Count header on every outbound delegation, rejecting requests exceeding a strict ceiling (typically 3–4 hops); (2) track visited agent IDs in a call-chain list to immediately block cyclic graphs (A → B → A); (3) propagate a decreasing deadline budget header so downstream agents abort before upstream timeouts; and (4) apply per-client SLA rate and token/request quotas in API Manager.

5. When designing an A2A Specialist response, when should data go into status.message versus artifacts?

Use status.message for conversational status updates, progress notes, error explanations, and input-required clarifying questions intended to guide dialogue. Place the durable, verifiable outputs of the task—such as an approved credit-memo JSON record, a generated PDF claim summary, or a risk-score vector—inside artifacts with typed data or file parts. Separating conversational wrapper text from structured artifacts lets upstream Mule flows and deterministic systems consume the output reliably without brittle regex parsing.
