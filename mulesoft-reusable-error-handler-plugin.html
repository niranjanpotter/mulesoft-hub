<?xml version="1.0" encoding="UTF-8"?>
<mule xmlns="http://www.mulesoft.org/schema/mule/core"
      xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core">
  <import file="corp-global-error-handler.xml"/>
  <configuration defaultErrorHandler-ref="Global_Enterprise_Error_Handler"/>

  <!-- Inside corp-global-error-handler.xml (packaged as reusable mule-plugin) -->
  <error-handler name="Global_Enterprise_Error_Handler">
    <on-error-propagate type="APIKIT:BAD_REQUEST">
      <set-variable variableName="httpStatus" value="400"/>
      <flow-ref name="build-canonical-error-json-subflow"/>
    </on-error-propagate>
    <on-error-propagate type="HTTP:CONNECTIVITY, HTTP:TIMEOUT">
      <set-variable variableName="httpStatus" value="504"/>
      <flow-ref name="build-canonical-error-json-subflow"/>
    </on-error-propagate>
    <on-error-propagate type="ANY">
      <set-variable variableName="httpStatus" value="500"/>
      <flow-ref name="build-canonical-error-json-subflow"/>
    </on-error-propagate>
  </error-handler>
</mule>

Real Setup — Follow Exactly

Project & Runtime Setup

Project Name: corp-error-handler-plugin (Mule XML SDK) · Target Runtime: Mule Runtime 4.9.x LTS · Reusable Mule Plugin JAR

pom.xml / CLI Setup 
<!-- Consuming microservice pom.xml adds just 1 dependency: -->
<dependency>
  <groupId>${corp.org.id}</groupId>
  <artifactId>corp-error-handler-plugin</artifactId>
  <version>2.1.0</version>
  <classifier>mule-plugin</classifier>
</dependency>

Architecture Deep-Dive Q&A

Q1 [PRODUCTION ARCHITECTURE] ⏱️ 3 min read

Why should an enterprise package its error handler as a shared Maven dependency rather than copying XML snippets?

🎯 HOW TO ANSWER (SENIOR ARCHITECT SCRIPT)

Copying error handling XML snippets leads to inconsistent HTTP status codes, varying error payload formats, and maintenance nightmares when corporate logging standards change. A shared Maven plugin enforces standardized RFC 7807 JSON error responses across all System, Process, and Experience APIs.

Q2 [PRODUCTION ARCHITECTURE] ⏱️ 3 min read

How do you propagate a System API error through a Process API to an Experience API cleanly?

🎯 HOW TO ANSWER (SENIOR ARCHITECT SCRIPT)

When SAPI returns HTTP 400/500, PAPI's HTTP request component catches it inside a Try scope. Rather than throwing a generic MULE:HTTP_INTERNAL_SERVER_ERROR, PAPI extracts error.errorMessage.payload and rethrows a custom BUSINESS:ERROR with the original SAPI error payload preserved.
